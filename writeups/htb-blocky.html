Enumeration

Mapping the Attack Surface

An Nmap scan reveals a mixed-purpose host: ProFTPD, OpenSSH, an Apache server running WordPress, and a Minecraft server (with an unresponsive Votifier listener on port 8192). The WordPress presence suggests the usual web-app attack surface, but the Minecraft server hints there's more to this box than a typical CMS pentest.

  • 21/tcp - ProFTPD
  • 22/tcp - OpenSSH
  • 80/tcp - Apache / WordPress
  • 8192/tcp - Minecraft Votifier (unresponsive)
  • 25565/tcp - Minecraft server

Directory Brute-Forcing

Standard WordPress + PHP wordlists generate too much noise on this site, so a directories-only brute force with a lowercase medium wordlist is used instead. This turns up a /plugins directory that is unrelated to WordPress's own wp-content/plugins path -- it's a separate folder serving Minecraft server plugin JARs directly over HTTP.

gobuster dir -u http://10.10.10.37/ -w /usr/share/wordlists/dirbuster/directory-list-lowercase-2.3-medium.txt -x '' 
...
/plugins (Status: 200)

Inside /plugins are two files: griefprevention.jar, a known open-source Minecraft plugin, and BlockyCore.jar -- a bespoke plugin clearly custom-written for this server.

Foothold

Decompiling BlockyCore.jar

A .jar file is just a zipped archive of compiled Java bytecode -- it can be decompiled back into near-readable source with a tool like JD-GUI in seconds. The assumption that a compiled artifact is "safe" to ship because it isn't human-readable turns out to be false here.

Mechanism first

Java bytecode retains most semantic structure of the original source (class/method/field names, string constants, control flow) unless deliberately obfuscated. Decompilers like JD-GUI, CFR, or Procyon reconstruct source that is functionally -- and often literally -- identical to what the developer wrote, including any hardcoded literals such as passwords.

Decompiling BlockyCore.jar exposes a hardcoded root MySQL password directly in the plugin's connection-handling code.

public class DBController {
    public static Connection getConnection() {
        String url = "jdbc:mysql://localhost:3306/minecraft";
        String user = "root";
        String pass = "8YsqfCTnvxAUeduzjhJHVK9G2"; // hardcoded credential
        ...
    }
}

A WordPress post on the site separately references the username notch (a nod to Minecraft's creator). Combined with the recovered password, this suggests a classic password-reuse scenario across the MySQL and OS layers.

SSH via Reused Credentials

The MySQL root password recovered from the JAR is tested directly against SSH for the notch user and works, granting immediate shell access and the user flag.

$ ssh notch@10.10.10.37
notch@10.10.10.37's password: 8YsqfCTnvxAUeduzjhJHVK9G2

notch@Blocky:~$ cat user.txt
e5a13....

An alternate, non-intended path exists: use the same DB creds to log into phpMyAdmin, change the WordPress admin password, upload a PHP reverse shell to get a www-data shell, then escalate via the DCCP double-free kernel exploit (CVE-2017-6074). This works but is considerably more involved than the direct credential-reuse route.

Privilege Escalation

Sudoers Group Membership

Running LinEnum on the box surfaces a large amount of system data, but the standout finding is immediate: the notch user is a member of the sudo group with no further restrictions in the sudoers configuration.

notch@Blocky:~$ id
uid=1000(notch) gid=1000(notch) groups=1000(notch),27(sudo)

notch@Blocky:~$ sudo -i
[sudo] password for notch: 8YsqfCTnvxAUeduzjhJHVK9G2
root@Blocky:~# whoami
root
Mechanism first

Unrestricted membership in the sudo/wheel group grants a user the ability to run any command as root after authenticating with their own password -- it is functionally equivalent to giving out the root password itself, just gated behind one extra `sudo` invocation.

With valid credentials already in hand and no command restrictions in place, escalation to root requires no exploit at all -- just exercising the privilege that was already granted.

Closing Thoughts

Lessons & Detection

  • Compiled is not secret. Java .jar files (and most unobfuscated compiled artifacts) decompile back into near-original source almost instantly. Hardcoding credentials in application code is never safe, regardless of whether the source itself is published.
  • Incidental leaks compound. A blog post, changelog, or plugin folder can leak a username or infrastructure detail that turns an isolated credential leak into a full account takeover once combined with a password found elsewhere.
  • Cross-service password reuse is a top real-world escalation vector -- a Minecraft plugin's database password reused as an OS-level SSH password turned a minor leak into full host compromise.
  • Unrestricted sudoers/wheel membership is equivalent to root access and should be audited with the same scrutiny as direct root credentials.

Detection-wise: scan deployed .jar/.class files for hardcoded credential patterns before they reach production, audit web-exposed directories for content that shouldn't be reachable at all (independent of sensitivity), periodically review sudoers/wheel group membership, and monitor for credential reuse across service boundaries where feasible via canary tokens.
