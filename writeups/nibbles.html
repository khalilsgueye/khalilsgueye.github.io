Nibbles

A default Apache page hides a vulnerable blogging CMS, a reused weak password, and a world-writable sudo script — three small mistakes that chain into full root.

00 Why this box matters

Nibbles is rated Easy, but the chain behind it is a near-perfect miniature of how real breaches happen: a forgotten or under-documented web application exposed on a production host, an admin account protected by a weak/guessable password, and a sudo rule that trusts a file the low-privilege user can edit. None of these individually requires deep exploit-dev skill — the danger is that each one is common in real environments, and stacked together they hand over the entire box.

The lesson for defenders isn't "patch this CVE." It's: audit what's actually reachable on port 80, rotate default/weak CMS credentials, and never let sudo trust a script whose ownership or permissions an attacker-controlled user can influence.

01 Recon

Port scan

Standard full TCP sweep first, since Easy boxes on HTB rarely hide services outside the obvious two.

 nmap
$ nmap -sC -sV -p- -T4 10.10.10.75
# trimmed
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 7.2p2 Ubuntu 4ubuntu2.2 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Apache httpd 2.4.18 ((Ubuntu))
|_http-title: Site doesn't have a title (text/html).
|_http-server-header: Apache/2.4.18 (Ubuntu)

Two services: SSH and a default-looking Apache install. The interesting surface is HTTP.

02 Web enumeration

The default page is a decoy

Visiting the root of the site shows the stock Apache2 Ubuntu Default Page — nothing to exploit there directly. But default pages are frequently left in place on top of a real application sitting in a subdirectory. Checking the HTML source and robots.txt both pay off here.

 enum
$ curl -s http://10.10.10.75/ | grep -i nibble
<!-- /nibbleblog/ -->

$ curl -s http://10.10.10.75/robots.txt
User-agent: *
Disallow: /nibbleblog/admin.php
Disallow: /nibbleblog/README.md
Mechanism first

This is plain information disclosure via developer artifacts: an HTML comment and a robots.txt entry both leak the existence of a hidden path that was never meant to be advertised to unauthenticated visitors. Search engines are told not to index it, but nothing stops a human (or a scanner) from just requesting it directly — robots.txt is a request, not an access control.

03 Identifying the CMS and its CVE

Browsing to /nibbleblog/ reveals a working blog install: Nibbleblog, a lightweight PHP CMS. The footer/README discloses the version — 4.0.3, a build with a known, publicly documented vulnerability.

 searchsploit
$ searchsploit nibbleblog
------------------------------------------------------------ ---------------------------------
 Exploit Title                                                |  Path
------------------------------------------------------------ ---------------------------------
Nibbleblog 4.0.3 - Arbitrary File Upload (Metasploit)         | php/webapps/38489.rb
------------------------------------------------------------ ---------------------------------

This corresponds to CVE-2015-6967: the My Image plugin, used to attach a header image to a blog, accepts uploaded files without validating their actual content type — only trusting the file extension check on the client side. An authenticated admin can therefore upload a PHP file disguised as an image and get it stored inside a web-reachable directory.

Crucially, this vulnerability requires authenticated admin access to the CMS. That's the next gap to close.

04 Credential access

Nibbleblog's admin panel sits at /nibbleblog/admin.php. Rather than brute-forcing blindly, a small guess based on the box's naming theme is worth trying first — a habit that pays off surprisingly often against CTF-style targets and, worryingly, against real organizations that reuse a branded or thematic password across systems.

 login
$ curl -s -i http://10.10.10.75/nibbleblog/admin.php \
    -d "username=admin&password=nibbles"
# 302 redirect to admin/index.php -> valid session cookie set
Mechanism first

This is weak/guessable credential reuse (T1110/T1078 territory) — no rate-limiting, no account lockout, no MFA on the admin login. A single low-entropy password themed after the application name was enough. In production, this is exactly the class of finding that shows up in every credential-stuffing and password-spray postmortem.

05 Exploitation — arbitrary file upload to RCE
Mechanism first

The My Image plugin's upload handler checks the file's declared MIME type / extension but never inspects or re-validates the actual bytes, and the upload directory is directly served by Apache with PHP execution enabled. Upload a file named with a benign image extension but containing a PHP payload (or simply a .php file if the extension filter is bypassable), request it directly, and the web server executes it as PHP. This is a textbook unrestricted file upload leading to remote code execution — CWE-434.

 msfconsole
$ msfconsole -q

$ id

Foothold obtained as the local user nibbler — the same account the Apache/PHP-FPM worker runs as on this box, which is itself a misconfiguration (web workers should run as a dedicated unprivileged service account, not a real interactive user).

06 Privilege escalation — sudo trusting a writable script

Standard privesc triage starts with checking what the current user is allowed to run as root.

 sudo -l
$ sudo -l
Matching Defaults entries for nibbler on nibbles:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User nibbler may run the following commands on nibbles:
    (root) NOPASSWD: /home/nibbler/personal/stuff/monitor.sh

$ ls -la /home/nibbler/personal/stuff/monitor.sh
-rwxr--r-- 1 nibbler nibbler 0 Jan  1 00:00 monitor.sh
Mechanism first

The sudoers rule allows nibbler to execute a specific script as root with no password prompt — a common and reasonable-looking pattern for delegating a monitoring task. The fatal flaw is that the script itself lives under /home/nibbler/ and is owned and writable by the same user it's granted to run as root. Sudo only checks the path in its policy; it does not verify the file's integrity, ownership immutability, or that it hasn't been altered since the rule was written. Whoever controls the file controls what root executes — this is abuse of sudo/sudo caching (T1548.003) via a mutable trusted binary.

 root
$ echo -e '#!/bin/bash\n/bin/bash -p' > /home/nibbler/personal/stuff/monitor.sh
$ sudo /home/nibbler/personal/stuff/monitor.sh
# id
uid=0(root) gid=0(root) groups=0(root)
# cat /root/root.txt
[REDACTED — grab your own]
07 Detection
  • Web layer: alert on POST requests to CMS admin/login endpoints with high request rates from a single source (credential guessing/spraying), and on file uploads that land executable extensions (.php, .phtml) inside directories intended for media.
  • Process/EDR layer: a PHP-FPM or Apache worker process spawning /bin/bash or a reverse shell is a high-fidelity indicator of webshell execution — CMS worker processes should almost never fork interactive shells.
  • Host layer: audit (auditd/execve logging) of every sudo invocation, especially against scripts outside /usr/bin or /usr/local. A sudo rule pointing at a path under a normal user's home directory should itself trip a config-drift alert.
  • File integrity monitoring (FIM): any modification to a script referenced by a NOPASSWD sudoers entry should generate an immediate alert — this is exactly the artifact that was silently rewritten in this attack.
08 Remediation
  1. Patch/replace the CMS. Nibbleblog 4.0.3 is EOL and carries a known unauthenticated-adjacent RCE path; upgrade or migrate off it, and validate all file uploads server-side by content inspection (magic bytes / re-encoding), never by extension or client-supplied MIME type alone.
  2. Remove exposure of hidden paths. Don't rely on robots.txt or obscurity to hide admin panels — put them behind network-level restrictions (VPN/allowlist) or at minimum strong authentication with rate limiting and MFA.
  3. Enforce credential hygiene. Ban default/thematic/dictionary passwords on CMS admin accounts; integrate with a password policy or SSO rather than local app auth.
  4. Run web workers as a dedicated low-privilege service account distinct from any real login user, with a restrictive shell and no home directory writable by the web app.
  5. Harden sudoers. Never grant NOPASSWD execution of a script that lives in a path writable by the grantee. Store privileged scripts under root-owned, mode 750 directories (e.g. /usr/local/sbin), owned by root, and reference them by absolute path with integrity pinning (checksum validation, or use sudo's command matching plus immutable attribute chattr +i where feasible).

Nibbles is a reminder that "easy" boxes are easy technically, not conceptually — the underlying weaknesses (leaked hidden paths, weak passwords, unrestricted uploads, and sudo rules that trust mutable files) are exactly what shows up in real breach reports every year. Each fix here is cheap; the cost only shows up when they're skipped.
