HTB - Mirai

An IoT box that's less about exploitation and more about reading fingerprints: a Pi-hole panel gives away hardware, hardware gives away defaults, and root.txt has to be carved out of raw disk bytes.

Enumeration

Recon

An Nmap sweep turns up OpenSSH, DNS, a lighttpd web server, and Plex/UPnP services. Port 80 itself just returns a blank page, which usually means there's something being served on a non-obvious path rather than nothing at all.

nmap -sC -sV -p- 10.10.10.48

PORT     STATE SERVICE
22/tcp   open  ssh
53/tcp   open  domain
80/tcp   open  http     lighttpd
1900/tcp open  upnp

gobuster dir -u http://10.10.10.48/ -w common.txt
/admin                (Status: 301)

Directory brute-forcing surfaces an /admin path that the blank root page never linked to.

Fingerprinting

From Web Panel to Default Creds

Loading /admin reveals a Pi-hole dashboard. Pi-hole isn't a vulnerability by itself, but it is a very strong fingerprint: it's almost exclusively deployed on small single-board Linux devices, overwhelmingly Raspberry Pi. That single observation chains into an OS identification, and the OS identification chains into a set of well-known default credentials.

Mechanism first

Web panels don't just leak app-level info — a branded piece of software tells you what hardware and OS stack it typically runs on. Device = Raspberry Pi → default OS = Raspbian → default OS-level account = pi:raspberry. SSH authenticates against OS accounts, not the web app, so this credential path is completely separate from the Pi-hole login itself.

ssh pi@10.10.10.48
Password: raspberry

pi@raspberrypi:~$ id
uid=1000(pi) gid=1000(pi) groups=1000(pi),...,27(sudo)

The pi user is in the sudo group by default on stock Raspbian installs, so authentication and full privilege escalation collapse into a single step.

Privilege Escalation

sudo su and a Missing Flag

pi@raspberrypi:~$ sudo su
root@raspberrypi:~# cat /home/pi/Desktop/user.txt
<user flag>

root@raspberrypi:~# cat /root/root.txt
I lost my original root.txt! I think I may have a backup on my USB stick...

root.txt has been intentionally removed and replaced with a note pointing at a USB stick, turning the last step of the box into a small forensics exercise instead of a technical escalation.

Forensics

Recovering root.txt from Raw Disk

Checking mounted filesystems finds the USB stick, but the flag file is gone from it and lost+found is empty — expected, since lost+found is only populated by filesystem-repair tools like fsck, not by a plain rm.

df -h
/dev/sdb   32M   ...   /media/usbstick

ls -la /media/usbstick
damnit.txt   # "I accidentally deleted my root.txt flag from the USB..."

ls /media/usbstick/lost+found
(empty)
Mechanism first

Deleting a file only removes its entry from the filesystem's index — the mapping of filename to data location — and marks that space reusable. It does not erase the actual bytes on disk; those persist until something else overwrites them. Reading the raw block device instead of the mounted, indexed view bypasses the filesystem's bookkeeping entirely and exposes every byte still physically present.

strings /dev/sdb | grep -A 3 -B 3 "root.txt"

...
root.txt
<32-char hex flag recovered from adjacent raw bytes>
...

The old filename reference and its adjacent data were still sitting on disk, letting strings pull the flag straight out of the raw device. (An equally valid approach: image the device with dcfldd, exfil the image via scp, and run strings/hexdump against it locally.)

Closing Thoughts

Lessons

  • Any exposed banner or branded admin panel — even one that isn't itself vulnerable — can fingerprint the underlying device and OS, and that identity often leads straight to known default credentials.
  • Default credentials combined with default excessive privileges (a low-priv user pre-added to sudoers) collapse "initial access" and "root" into a single step.
  • Deletion is not erasure. Scanning a raw block device for strings or known filenames can recover data the filesystem no longer indexes — the same principle underlying real-world digital forensics and incident response.
