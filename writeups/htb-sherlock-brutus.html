HTB Sherlock: Brutus

Reconstructing an SSH brute-force root compromise purely from auth.log and wtmp artifacts.

Target
Confluence Linux Server (auth.log / wtmp)
Platform
Linux
Difficulty
Very Easy
Root cause
Misconfiguration — SSH Brute Force with Direct Root Login Allowed
ATT&CKT1110T1110.001T1078T1021.004
Scenario

Overview

Brutus is a Very Easy HTB Sherlock — a blue-team forensics exercise rather than an offensive box. The premise: a Linux server running Confluence was hit with an SSH brute-force attack and the attacker got in. The task is purely reconstructive — walk two log artifacts backward to build an accurate timeline of the intrusion.

  • auth.log — plaintext SSH authentication log recording every login attempt, success or failure.
  • wtmp — binary login/session accounting file, parsed with last or utmpdump.

Worked from a Kali VM since wtmp's binary utmp-style format isn't cleanly readable on macOS without extra tooling.

Enumeration

Identifying the Brute-Force Source

First pass was scanning auth.log for the classic brute-force signature: a burst of repeated Failed password / Invalid user lines from a single source IP, ramping up over a short window.

grep "Failed password" auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr
grep "sshd" auth.log | grep -E "Invalid user|Failed password" | head -n 30

The flood of failures began around 06:31 and came consistently from a single attacking IP — confirming a scripted brute-force rather than scattered opportunistic probing.

Mechanism first

SSH brute-forcing works because there's no built-in rate limiting on failed authentication attempts by default. Without fail2ban, sshguard, or similar, an attacker can throw thousands of password guesses at a service with zero friction — the log just fills with linear, high-frequency Failed password entries from one source until something eventually lands.

Foothold

From Failed Password to Accepted Password

Scanning forward through the flood of failures for the transition point — the line where Failed password flips to Accepted password for a specific account — marks the moment of initial access.

grep "Accepted password" auth.log

The account that got successfully brute-forced was root itself — the worst-case outcome for this attack class. There's no privilege escalation step needed downstream because the attacker landed with full administrative access on the very first successful login.

Mechanism first

Direct root SSH login (PermitRootLogin yes) collapses the entire kill chain into a single step. Normally an attacker needs a foothold plus a separate privesc chain; here, brute-forcing the root password over SSH is the privesc — there's no intermediate low-priv account to pivot from.

Privilege Escalation

None Required — Root Achieved on Landing

Because the compromised credential was root's own password, there is no separate privilege escalation phase to trace in this incident — the attacker's very first authenticated session already carried full system access. The forensic question shifts instead to distinguishing automated brute-force noise from a genuine, hands-on-keyboard session.

auth.log alone is ambiguous here: brute-force tooling can continue hammering the box from the same or other IPs after the successful login, so a second or third Accepted password line doesn't necessarily mean the attacker manually logged in to act on the access. wtmp resolves this ambiguity.

utmpdump wtmp | grep -A2 -B2 "root"
last -f wtmp | head -n 20

wtmp's session records — login time, session duration, TTY/pts allocation — make it possible to isolate the one login that actually held an open interactive session (a real terminal, non-trivial duration) versus rapid-fire auth attempts with no session lifetime. That session's timestamp is the true moment the attacker began manually operating on the box.

Mechanism first

auth.log records authentication events; wtmp records session lifecycle. Cross-referencing the two turns a list of login attempts into an actual behavioral timeline — automated tooling produces auth events with no meaningful session tail, while a human operator produces a session with real elapsed time and an assigned pty.

Closing Thoughts

Preventable by Design, Not Exotic Technique

The entire finding chain reduces to three unremarkable but critical gaps: SSH exposed to brute-force with no rate limiting, no lockout/fail2ban in front of it, and root permitted to authenticate directly over SSH. None of this required anything exotic on the attacker's side — it's a textbook credential-stuffing brute force that only succeeded because basic hardening was absent.

The real value of this Sherlock is methodological: correlating a plaintext log (auth.log) against a binary session-accounting artifact (wtmp) turns two individually ambiguous data sources into one trustworthy timeline. Trusting either file in isolation would have left gaps — auth.log can't cleanly separate bot noise from operator activity, and wtmp alone doesn't explain why access was gained in the first place.

  • Disable direct root SSH login; force privilege escalation through sudo with a named account.
  • Deploy fail2ban / sshguard or equivalent rate limiting on SSH.
  • Move to key-based authentication and disable password auth entirely.
  • Centralize and retain both auth.log and wtmp for real incident timelines rather than log rotation defaults.
