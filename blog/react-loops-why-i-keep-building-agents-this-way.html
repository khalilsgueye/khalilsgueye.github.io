ReAct Loops: Why I Keep Building Agents This Way

A look at the Reason + Act pattern that underlies every agent I've built so far, and why I keep choosing it over more complex multi-agent frameworks.

AI AgentsSoftware ArchitectureReActLLMs

I want to go into some detail on the ReAct pattern, because it's the architecture behind basically everything I've built so far — the CSV brief agent, the writeup publishing bots, all of it — and I think it's worth explaining why I keep reaching for it over other agent designs.

ReAct stands for Reason + Act. The shape of it is simple: the model reasons about what to do next, picks a tool, the tool actually runs, the result gets fed back into the model's context, and it reasons again with that new information. Repeat until the model decides it's done. That's the whole architecture. No separate planning phase, no fixed pipeline of steps decided in advance — the model figures out the next move at every single step, informed by everything that's happened so far.

Why I like it over other approaches:

  • Transparency. Every single decision the model makes is visible — you can literally print out "the model chose tool X with these inputs" at every step and watch the whole reasoning trail unfold. Compare that to more opaque multi-agent frameworks where agents hand off to each other through some internal orchestration layer you can't easily inspect. With ReAct, if something goes wrong, you can point to the exact tool call that caused it.
  • It's just Python. There's no special framework required — it's a loop, a dispatch table mapping tool names to functions, and an API call. You can write the whole thing in under 300 lines and understand every part of it. That matters a lot to me because I want to actually own the systems I'm building, not depend on a black-box library that abstracts the loop away from me.
  • Versatility. Because the "tools" are just Python functions with a schema attached, you can hand the model access to almost anything — a database query, a web search, a regression, a file write. The loop doesn't care what the tools do.

The part I find most interesting: tools can generate more agents. A tool doesn't have to be a simple, static function — it can itself spin up another instance of the loop, with its own system prompt and its own tool set, and return that sub-agent's final output as the tool result. So you can have an orchestrating ReAct loop that, instead of calling a "search the web" function, calls a "delegate this entire research task to a sub-agent" function — and that sub-agent runs its own full ReAct loop before handing back a result. It's recursive in a genuinely useful way, and it's still just the same simple pattern all the way down.
