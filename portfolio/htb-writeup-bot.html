HTB Writeup Bot

After rooting a machine, the last thing you want to do is sit down and write it up. This agent removes that step. I record a voice note walking through the box; it transcribes the audio on my own machine, drafts a structured writeup with Claude, and commits the finished page straight to this site — no editor, no copy-paste, no server to babysit. Every writeup in the Writeups section is published by this pipeline.

Python Whisper Claude API Telegram GitHub API Docker

How it works

Five stages, each isolated so a failure in one is legible and recoverable rather than a silent dead end. The bot reaches out to Telegram rather than being reached, so it runs from home with no public endpoint exposed.

01

Capture

A Telegram voice note triggers everything. The bot long-polls Telegram — it asks for new messages rather than exposing a webhook — so nothing inbound has to reach the machine. Every message is checked against a single allowed user ID, so only I can drive it.

02

Transcribe — locally

The audio is transcribed by faster-whisper running the large-v3-turbo model on-device. No transcription API, no per-minute cost, and the recording never leaves the machine. The model loads once and stays resident, so an idle bot costs nothing to keep running.

03

Draft

The transcript goes to Claude under a strict prompt that returns JSON only — title, metadata, categories, and an HTML body built from a fixed block vocabulary. The model reasons over what I said; it does not get to invent the page's structure.

04

Render

That JSON is poured into a static HTML template. Categories become tag chips, the body slots into a page shell whose markup and styling are fixed — so every writeup comes out visually identical, no matter what the model wrote.

05

Publish

The finished page is committed through the GitHub Contents API, and the index page is updated to link it. GitHub Pages rebuilds within a minute, and the bot replies with the live URL.

Why transcription runs locally

Security transcripts are dense with terms a general model mishears — CVE numbers, tool names, field names like is_admin. Running a strong Whisper model on-device keeps those intact, costs nothing per run, and keeps the raw recording private. The only paid call in the whole pipeline is the single Claude draft.

Structure is the template's job, not the model's

The riskiest part of letting a model publish is that it drifts — different headings, different markup, a broken layout on a bad day. This pipeline removes that freedom. The model returns content as constrained JSON; a fixed template owns every tag and every style rule. The result is consistency by construction: the model can write a better or worse writeup, but it can't produce a worse-looking page.

Publishing is a read-modify-write, not an overwrite

Adding a writeup means two commits: a brand-new page, and a surgical edit to the index. The index update fetches the current file and its version hash, inserts a single row at a fixed marker, increments the count, and writes it back with that hash attached. The hash is what makes it safe — GitHub rejects the write if the file changed underneath it, so the index can never be silently clobbered.

the publish call, in essence
PUT /repos/<user>/<user>.github.io/contents/writeups/<slug>.html
{
  "message": "Add <machine> writeup",
  "content": "<base64 of the rendered page>",
  "branch":  "main"
}
# the index gets the same treatment, but with the current
# file hash attached so the edit can't overwrite a stale copy

Always-on, without a fragile setup

The whole thing runs in a container with a restart policy, so it survives crashes and reboots on its own. Two volumes persist across rebuilds: the Whisper model cache, so the 1.6 GB download happens once, and an archive folder that keeps every raw transcript and finished page — a durable record even if a later step ever fails.

Applied uses

The security writeup is one instance of a general pattern: speak a structured thing, get a published, consistently formatted artifact — with no manual formatting step in between.

  • Call and meeting debriefs. Talk through a call on the walk back to your desk; get a structured summary committed to a shared repo or wiki, formatted the same way every time.
  • Field and inspection reports. Dictate observations on site; get a formatted report with fixed sections, ready to file — useful anywhere the person doing the work isn't at a keyboard.
  • Release notes and changelogs. Describe what shipped right after a deploy; get a clean, consistent entry appended to the log automatically.
  • Reading and research notes. Narrate what you took from a paper or a session; grow a structured, searchable knowledge base without stopping to format anything.

The reusable core is the same in every case: private, local transcription, an LLM constrained by a template so output stays uniform, and git-based publishing that leaves a full history — with a review gate dropped in whenever a draft shouldn't go straight to live.
